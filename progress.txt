REPOSITORY PATTERN

El repository define un contrato asíncrono:

src/repositories/UserRepository.ts

export interface UserRepository {
  save(user: User): Promise<User>;
  findAll(): Promise<User[]>;
  findById(id: string): Promise<User | undefined>;
}

La implementación actual sigue siendo InMemoryUserRepository,
pero ya cumple el contrato async:

src/repositories/InMemoryUserRepository.ts

Todos los métodos son async y devuelven Promise<...>,
aunque la persistencia sigue siendo un array en memoria.

Decisión:
- el contrato async fue introducido como preparación para
  una persistencia real (PostgreSQL);
- InMemoryUserRepository se adaptó para cumplir el contrato
  sin cambiar su comportamiento observable.

DECISIONES SOBRE EL CONTRATO DEL REPOSITORY

save recibe un User, no un CreateUserDto.

Motivo:
- CreateUserDto representa datos provenientes de HTTP.
- User representa la entidad que el service ha construido.
- El repository se ocupa de persistir la entidad.
- El repository no debe depender de conceptos HTTP/DTO.

Flujo:

CreateUserDto
 ↓
Service
 ↓
User + UUID
 ↓
Repository.save(User)

findById devuelve:

Promise<User | undefined>

Motivo:
- que un usuario no exista no es necesariamente un error de persistencia;
- el repository informa de que no existe;
- el service decide que eso constituye un error de negocio.

Flujo:

Repository
 ↓
undefined
 ↓
Service
 ↓
NotFoundError

El repository NO conoce HTTP ni 404.

ERRORES DE PERSISTENCIA

No queremos utilizar undefined, null o never como mecanismo genérico de error para save.

La decisión actual es:

save()
 ├── éxito → User
 └── error → throw error

never no es un tipo apropiado para representar un posible fallo de persistencia.

IN-MEMORY REPOSITORY

Existe:

src/repositories/InMemoryUserRepository.ts

Implementa:

UserRepository

La implementación actual es:

export class InMemoryUserRepository implements UserRepository {
  constructor(private users: User[] = []) {}

  async save(user: User): Promise<User> {
    this.users.push(user);
    return user;
  }

  async findAll(): Promise<User[]> {
    return [...this.users];
  }

  async findById(id: string): Promise<User | undefined> {
    return this.users.find((user) => user.id === id);
  }
}

Todos los métodos son async para cumplir el contrato de UserRepository.

ENCAPSULACIÓN DEL IN-MEMORY REPOSITORY

No devolvemos directamente:

return this.users;

sino:

return [...this.users];

Motivo:

Evitar que código externo pueda modificar directamente el array interno mediante:

repository.findAll().push(user);

Con la copia superficial, esa operación modifica únicamente la copia.

Actualmente NO hemos introducido copia profunda de los objetos User.

Decisión:
- no añadir complejidad adicional mientras no sea necesaria.

DECISIONES ARQUITECTÓNICAS YA TOMADAS

No volver a cuestionar innecesariamente estas decisiones salvo que aparezca una razón nueva:

1. El service utiliza Repository Pattern.
2. El repository se define mediante una interfaz.
3. El contrato del repository es asíncrono (Promise<...>).
4. InMemoryUserRepository es la implementación actual.
5. UsersService depende de UserRepository, no de InMemoryUserRepository.
6. UsersController depende de UsersService.
7. app.ts actúa como Composition Root.
8. Dependency Injection se hace manualmente.
9. No se utiliza ningún contenedor DI.
10. Los controllers se adaptan a Express mediante asyncHandler desde las rutas.
11. Los controllers son async con await sobre las llamadas al service.
12. Los services son async con await sobre las llamadas al repository.
13. findById devuelve Promise<User | undefined>.
14. El service transforma un usuario inexistente en NotFoundError.
15. Los repositories no conocen HTTP.
16. El service no conoce Express.
17. El DTO pertenece al límite de entrada de la aplicación; el repository trabaja con User.
18. La persistencia actual sigue siendo un array en memoria, pero el contrato ya es async.
19. Se ha preparado infraestructura PostgreSQL (docker-compose, .env, pg Pool, test script) sin integrarla todavía.
20. Las variables de entorno se cargan con node --env-file, sin dependencias externas.
21. No se ha creado PostgresUserRepository todavía.
22. No introducir factories, DI containers ni otras abstracciones mientras no sean necesarias.
23. No añadir complejidad de encapsulación adicional, como deep cloning, mientras no exista una necesidad real.
24. No convertir clases o funciones simplemente por seguir un patrón; las decisiones deben responder a una necesidad concreta.
25. El controller se ha convertido en clase porque necesita conservar su dependencia con UsersService.
26. Las rutas reciben el controller mediante createUsersRoutes(usersController).
27. app.ts construye manualmente las dependencias.
28. bind se realiza en las rutas y no dentro del controller.
29. El repository trabaja con User, no con CreateUserDto.
30. Los errores de negocio, como usuario no encontrado, se deciden en el service y no en el repository.
31. La API externa no debe cambiar como consecuencia de refactorizaciones internas salvo que se decida explícitamente.
