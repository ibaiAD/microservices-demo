import type { RequestHandler } from "express";

export function asyncHandler(fn: RequestHandler): RequestHandler {
  return (req, res, next) => {
    Promise.resolve(fn(req, res, next)).catch(next);
  };
}

Motivo:
- preparar Express para controllers async y errores provenientes de Promises.

Decisión:
- Los controllers se envuelven desde las rutas.
- No se envuelven internamente.
- La adaptación a Express pertenece a la capa HTTP.

REPOSITORY PATTERN

El cambio arquitectónico más reciente ha sido introducir Repository Pattern.

Antes:

Controller
 ↓
Service
 ↓
users[]

Ahora:

Controller
 ↓
Service
 ↓
UserRepository
 ↓
InMemoryUserRepository
 ↓
users[]

Objetivo:
- separar las reglas de negocio del acceso a datos.

El UsersService ya NO debe conocer directamente el array donde se almacenan los usuarios.

USER REPOSITORY

Existe:

src/repositories/UserRepository.ts

Contrato actual:

export interface UserRepository {
  save(user: User): User;
  findAll(): User[];
  findById(id: string): User | undefined;
}

DECISIONES SOBRE EL CONTRATO DEL REPOSITORY

save recibe un User, no un CreateUserDto.

Motivo:
- CreateUserDto representa datos provenientes de HTTP.
- User representa la entidad que el service ha construido.
- El repository se ocupa de persistir la entidad.
- El repository no debe depender de conceptos HTTP/DTO.

Actualmente el service genera el UUID y construye el User.

Flujo:

CreateUserDto
 ↓
Service
 ↓
User + UUID
 ↓
Repository.save(User)

No hemos decidido todavía si en una futura base de datos el ID seguirá siendo generado por el service o por la base de datos.

No anticipar esa decisión todavía.

findById devuelve:

User | undefined

Motivo:
- que un usuario no exista no es necesariamente un error de persistencia;
- el repository informa de que no existe;
- el service decide que eso constituye un error de negocio.

Flujo:

Repository
 ↓
undefined
 ↓
Service
 ↓
NotFoundError

El repository NO conoce HTTP ni 404.

ERRORES DE PERSISTENCIA

No queremos utilizar undefined, null o never como mecanismo genérico de error para save.

La decisión actual es:

save()
 ├── éxito → User
 └── error → throw error

never no es un tipo apropiado para representar un posible fallo de persistencia.

IN-MEMORY REPOSITORY

Existe:

src/repositories/InMemoryUserRepository.ts

Implementa:

UserRepository

La implementación actual es:

export class InMemoryUserRepository implements UserRepository {
  constructor(private users: User[] = []) {}

  save(user: User): User {
    this.users.push(user);
    return user;
  }

  findAll(): User[] {
    return [...this.users];
  }

  findById(id: string): User | undefined {
    return this.users.find((user) => user.id === id);
  }
}

CONSTRUCTOR DEL IN-MEMORY REPOSITORY

Se utiliza:

constructor(private users: User[] = []) {}

No hace falta:

constructor(private users: User[] = []) {
  this.users = users;
}

porque TypeScript ya realiza la asignación mediante parameter property.

Permite:

new InMemoryUserRepository()

para empezar vacío.

También permite proporcionar usuarios iniciales:

new InMemoryUserRepository(initialUsers)

Esto puede ser útil para tests.

ENCAPSULACIÓN DEL IN-MEMORY REPOSITORY

No devolvemos directamente:

return this.users;

sino:

return [...this.users];

Motivo:

Evitar que código externo pueda modificar directamente el array interno mediante:

repository.findAll().push(user);

Con la copia superficial, esa operación modifica únicamente la copia.

Actualmente NO hemos introducido copia profunda de los objetos User.

Decisión:
- no añadir complejidad adicional mientras no sea necesaria.

USERS SERVICE

UsersService anteriormente era un conjunto de funciones.

Se decidió convertirlo en clase porque ahora tiene una dependencia que necesita conservar:

UsersService
 ↓
UserRepository

Implementación actual:

import { randomUUID } from "node:crypto";

import { NotFoundError } from "../errors/NotFoundError.js";
import type { UserRepository } from "../repositories/UserRepository.js";
import type { CreateUserDto, User } from "../types/user.js";

export class UsersService {
  constructor(private userRepository: UserRepository) {}

  createUser(userData: CreateUserDto): User {
    const newId = randomUUID();

    const newUser = {
      id: newId,
      ...userData,
    };

    return this.userRepository.save(newUser);
  }

  getUsers(): User[] {
    return this.userRepository.findAll();
  }

  getUserById(id: string): User {
    const user = this.userRepository.findById(id);

    if (!user) {
      throw new NotFoundError("User not found");
    }

    return user;
  }
}

IMPORTANTE SOBRE EL SERVICE

El antiguo:

const users: User[] = [];

que existía en el service fue eliminado.

El service no debe tener su propio almacenamiento.

Responsabilidades actuales del service:
- generar UUID;
- construir el User;
- aplicar reglas de negocio;
- decidir que un usuario inexistente implica NotFoundError;
- delegar persistencia al repository.

No debe:
- conocer arrays internos del repository;
- conocer HTTP;
- devolver respuestas Express;
- gestionar res.status(...).

USERS CONTROLLER

Ahora es una clase:

src/controllers/users.controller.ts

Implementación actual:

import type { Request, Response } from "express";
import type { UsersService } from "../services/users.service.js";
import type { CreateUserDto, User } from "../types/user.js";

export class UsersController {
  constructor(private usersService: UsersService) {}

  async createNewUser(req: Request, res: Response) {
    const userData: CreateUserDto = req.body;

    const newUser = this.usersService.createUser(userData);

    res.status(201).json(newUser);
  }

  async getAllUsers(_req: Request, res: Response) {
    const users: User[] = this.usersService.getUsers();

    res.json(users);
  }

  async getUser(req: Request, res: Response) {
    const id = req.params.id as string;

    const user = this.usersService.getUserById(id);

    res.json(user);
  }
}

MOTIVO DE CONVERTIR EL CONTROLLER EN CLASE

Queríamos expresar explícitamente su dependencia:

constructor(private usersService: UsersService) {}

No se decidió que los controllers deban ser clases como regla general.

Fue una decisión pragmática para este proyecto porque el controller necesita conservar una dependencia.

El controller:
- conoce Express;
- recibe Request;
- genera respuestas HTTP;
- delega la lógica al service.

No conoce:
- repositories;
- arrays;
- persistencia;
- UUID;
- reglas de almacenamiento.

USERS ROUTES

Ya no exportamos directamente un Router.

Existe:

src/routes/users.routes.ts

Exporta:

createUsersRoutes(usersController)

Implementación actual:

import { Router } from "express";

import type { UsersController } from "../controllers/users.controller.js";
import { validateCreateUser } from "../middlewares/validateCreateUser.js";
import { asyncHandler } from "../utils/asyncHandler.js";

export function createUsersRoutes(usersController: UsersController) {
  const router = Router();

  router.post(
    "/users",
    validateCreateUser,
    asyncHandler(usersController.createNewUser.bind(usersController)),
  );

  router.get(
    "/users",
    asyncHandler(usersController.getAllUsers.bind(usersController)),
  );

  router.get(
    "/users/:id",
    asyncHandler(usersController.getUser.bind(usersController)),
  );

  return router;
}

BIND EN LAS RUTAS

Usamos:

usersController.getUser.bind(usersController)

porque Express recibe una referencia al método y puede ejecutarlo sin el contexto original de la instancia.

bind garantiza que:

this

siga apuntando al UsersController.

No hemos introducido otras técnicas de binding.

APP.TS / COMPOSITION ROOT

app.ts es actualmente el punto donde ensamblamos las dependencias.

Implementación actual:

import express from "express";

import { UsersController } from "./controllers/users.controller.js";
import { errorHandler } from "./middlewares/errorHandler.js";
import { InMemoryUserRepository } from "./repositories/InMemoryUserRepository.js";
import type { UserRepository } from "./repositories/UserRepository.js";

La línea:

Decisión:

- no introducir factories o contenedores mientras no sean necesarios.

DECISIONES ARQUITECTÓNICAS YA TOMADAS

No volver a cuestionar innecesariamente estas decisiones salvo que aparezca una razón nueva:

1. El service utiliza Repository Pattern.
2. El repository se define mediante una interfaz.
3. InMemoryUserRepository es la implementación actual.
4. UsersService depende de UserRepository, no de InMemoryUserRepository.
5. UsersController depende de UsersService.
6. app.ts actúa como Composition Root.
7. Dependency Injection se hace manualmente.
8. No se utiliza ningún contenedor DI.
9. Los controllers se adaptan a Express mediante asyncHandler desde las rutas.
10. Los controllers son async para preparar la futura persistencia asíncrona.
11. findById devuelve User | undefined.
12. El service transforma un usuario inexistente en NotFoundError.
13. Los repositories no conocen HTTP.
14. El service no conoce Express.
15. El DTO pertenece al límite de entrada de la aplicación; el repository trabaja con User.
16. El almacenamiento sigue siendo un array en memoria.
17. No introducir PostgreSQL, Docker, Kafka, factories, DI containers ni otras abstracciones hasta que sean necesarias.
18. No añadir complejidad de encapsulación adicional, como deep cloning, mientras no exista una necesidad real.
19. No convertir clases o funciones simplemente por seguir un patrón; las decisiones deben responder a una necesidad concreta.
20. El controller se ha convertido en clase porque necesita conservar su dependencia con UsersService.
21. Las rutas reciben el controller mediante createUsersRoutes(usersController).
22. app.ts construye manualmente las dependencias.
23. bind se realiza en las rutas y no dentro del controller.
24. El repository trabaja con User, no con CreateUserDto.
25. Los errores de negocio, como usuario no encontrado, se deciden en el service y no en el repository.
26. La API externa no debe cambiar como consecuencia de refactorizaciones internas salvo que se decida explícitamente.

PUNTO EXACTO DONDE CONTINUAR

El bloque de Repository Pattern + Dependency Injection manual está terminado.

El código funciona.

El proyecto se deja deliberadamente en este estado por ahora.

El siguiente bloque previsto es estudiar cómo cambiar el repository para una persistencia real.

El siguiente problema conceptual que debemos abordar es:

Array:

findById() → User | undefined

Base de datos:

findById() → Promise<User | undefined>

Una persistencia real normalmente será asíncrona.

Por tanto, antes de introducir PostgreSQL, Docker o cualquier base de datos, debemos explicar y modificar progresivamente el contrato para soportar operaciones asíncronas.

Posible evolución:

UserRepository
 ↓
métodos async
 ↓
Promise<User>
Promise<User[]>
Promise<User | undefined>

Eso obligará a propagar async/await:

Repository
 ↓
Service
 ↓
Controller
 ↓
asyncHandler
