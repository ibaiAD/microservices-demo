import type { NextFunction, Request, Response } from "express";
import type { CreateUserDto } from "../types/user.js";

export function validateCreateUser(
  req: Request,
  res: Response,
  next: NextFunction,
) {
  const user: CreateUserDto = req.body;
  if (!user.name || !user.email) {
    return res.status(400).json({
      error: "name and email are required",
    });
  }

  next();
}

La validación se aplica desde users.routes.ts:

router.post(
  "/users",
  validateCreateUser,
  asyncHandler(usersController.createNewUser.bind(usersController)),
);

DECISIÓN SOBRE LA VALIDACIÓN

Hemos decidido que las validaciones relacionadas con la entrada HTTP deben estar en el middleware.

Ejemplos de validaciones que pertenecen al middleware:

* name obligatorio;
* name string;
* name no vacío;
* email obligatorio;
* email string;
* email no vacío;
* formato básico de email, si decidimos exigirlo.

Las reglas que dependen del estado de la aplicación o de la base de datos no pertenecen al middleware.

Por ejemplo:

email ya existente
↓
Repository/PostgreSQL
↓
ConflictError
↓
HTTP 409

No debemos mover esa lógica al middleware.

DECISIÓN SOBRE LIBRERÍA DE VALIDACIÓN

Hemos decidido introducir una librería de validación para no escribir manualmente lógica de validación mediante muchos if.

La librería elegida es Zod.

Motivo:

* permite definir el esquema de validación de forma declarativa;
* permite relacionar el esquema runtime con los tipos de TypeScript;
* evita tener dos fuentes de verdad independientes;
* es suficiente para el tamaño actual del proyecto;
* no queremos introducir clases, decoradores ni una arquitectura de validación compleja.

Se han considerado otras alternativas como Joi, Yup o express-validator, pero para este proyecto se ha elegido Zod.

DECISIÓN SOBRE User Y CreateUserDto

User representa la entidad de la aplicación:

id
name
email

CreateUserDto representa los datos provenientes de HTTP:

name
email

No tienen el mismo propósito.

El flujo es:

CreateUserDto
↓
UsersService
↓
User + UUID
↓
Repository

El cliente HTTP no decide el id.

El repository recibe User, no CreateUserDto.

No cambiar esta decisión.

CONTROLLER ACTUAL

src/controllers/UsersController.ts:

import type { Request, Response } from "express";
import type { UsersService } from "../services/users.service.js";
import type { CreateUserDto, User } from "../types/user.js";

export class UsersController {
  constructor(private usersService: UsersService) {}

  async createNewUser(req: Request, res: Response) {
    const userData: CreateUserDto = req.body;
    const newUser = await this.usersService.createUser(userData);

    res.status(201).json(newUser);
  }

  async getAllUsers(_req: Request, res: Response) {
    const users: User[] = await this.usersService.getUsers();

    res.json(users);
  }

  async getUser(req: Request, res: Response) {
    const id = req.params.id as string;

    const user = await this.usersService.getUserById(id);

    res.json(user);
  }
}

IMPORTANTE SOBRE req.body Y TYPESCRIPT

Hemos identificado que:

const userData: CreateUserDto = req.body;

NO valida runtime.

La anotación TypeScript solo expresa un tipo estático.

Por ejemplo, una petición como:

{
  "name": 123,
  "email": true
}

podría pasar la validación actual porque validateCreateUser únicamente comprueba truthiness.

Por eso estamos introduciendo Zod.

No asumir que el tipo TypeScript por sí solo valida req.body.

REPOSITORY PATTERN

}

El contrato es asíncrono porque la persistencia real utiliza PostgreSQL.

DECISIONES SOBRE EL CONTRATO DEL REPOSITORY

save recibe User, no CreateUserDto.

Motivo:

* CreateUserDto representa datos provenientes de HTTP.
* User representa la entidad que el service ha construido.
* El repository se ocupa de persistir la entidad.
* El repository no debe depender de conceptos HTTP/DTO.

Flujo:

CreateUserDto
↓
Service
↓
User + UUID
↓
Repository.save(User)

findById devuelve:

Promise<User | undefined>

Motivo:

* que un usuario no exista no es necesariamente un error de persistencia;
* el repository informa de que no existe;
* el service decide que eso constituye un error de negocio.

Flujo:

Repository
↓
undefined
↓
Service
↓
NotFoundError

El repository NO conoce HTTP ni 404.

ERRORES DE PERSISTENCIA

save():

* éxito → User
* error → throw error

No se utiliza undefined, null o never como mecanismo genérico de error para save.

El repository deja propagarse los errores de PostgreSQL salvo los errores específicos que hemos decidido traducir.

Implementación actual de save():

async save(user: User): Promise<User> {
  let result: QueryResult<User>;

  try {
    result = await this.pool.query<User>(
      `
        INSERT INTO users (id, name, email)
        VALUES ($1, $2, $3)
        RETURNING id, name, email
      `,
      [user.id, user.name, user.email],
    );
  } catch (error) {
    if (error instanceof Error && "code" in error && error.code === "23505") {
      throw new ConflictError("A unique constraint was violated");
    }

    throw error;
  }

  const savedUser = result.rows[0];

  if (!savedUser) {
    throw new Error("User was inserted but could not be retrieved");
  }

  return savedUser;
}

IMPORTANTE SOBRE EL MANEJO DE UNIQUE

Se probó realmente un email duplicado.

PostgreSQL/pg proporcionó:

code: "23505"
constraint: "users_email_key"
detail: "Key (email)=(...) already exists."
table: "users"

Decisión tomada:

Cualquier error PostgreSQL con code === "23505" se traduce a ConflictError.

No se limita únicamente a users_email_key.

Motivo:

En el futuro podrían existir otras restricciones UNIQUE y no queremos acoplar el mecanismo a email.

Por ahora NO se introduce información sobre el atributo que produjo el conflicto.

No se analiza el texto de error.

No se expone users_email_key al cliente.

No se ha creado un type guard separado porque sería sobre-ingeniería para un único caso.

La traducción ocurre en PostgresUserRepository:

PostgreSQL 23505
↓
ConflictError
↓
errorHandler
↓
HTTP 409

El repository conoce el error técnico y lo traduce a un error de aplicación.

El errorHandler no conoce PostgreSQL.

No se ha introducido información específica del atributo porque no existe todavía una necesidad real.
