REPOSITORY PATTERN

El repository define un contrato asíncrono:

src/repositories/UserRepository.ts

export interface UserRepository {
save(user: User): Promise<User>;
findAll(): Promise<User[]>;
findById(id: string): Promise<User | undefined>;
}

El contrato es asíncrono porque la persistencia real utiliza PostgreSQL.

DECISIONES SOBRE EL CONTRATO DEL REPOSITORY

save recibe un User, no un CreateUserDto.

Motivo:

* CreateUserDto representa datos provenientes de HTTP.
* User representa la entidad que el service ha construido.
* El repository se ocupa de persistir la entidad.
* El repository no debe depender de conceptos HTTP/DTO.

Flujo:

CreateUserDto
↓
Service
↓
User + UUID
↓
Repository.save(User)

findById devuelve:

Promise<User | undefined>

Motivo:

* que un usuario no exista no es necesariamente un error de persistencia;
* el repository informa de que no existe;
* el service decide que eso constituye un error de negocio.

Flujo:

Repository
↓
undefined
↓
Service
↓
NotFoundError

El repository NO conoce HTTP ni 404.

ERRORES DE PERSISTENCIA

No queremos utilizar undefined, null o never como mecanismo genérico de error para save.

La decisión actual es:

save()
├── éxito → User
└── error → throw error

never no es un tipo apropiado para representar un posible fallo de persistencia.

El repository deja propagarse los errores de PostgreSQL.

ENCAPSULACIÓN DEL IN-MEMORY REPOSITORY

InMemoryUserRepository sigue existiendo:

Implementa UserRepository.

Implementación:

export class InMemoryUserRepository implements UserRepository {
constructor(private users: User[] = []) {}

async save(user: User): Promise<User> {
this.users.push(user);
return user;
}

async findAll(): Promise<User[]> {

}

Todos los métodos son async para cumplir el contrato.

Motivo:

No se utiliza copia profunda porque no es necesaria actualmente.

Índices:

DECISIONES SOBRE LA TABLA

La entidad User actual es:

id: string;
name: string;
email: string;

Correspondencia PostgreSQL:

id → UUID
name → VARCHAR
email → VARCHAR

Restricciones:

id → PRIMARY KEY
name → NOT NULL
email → NOT NULL UNIQUE

El UUID lo genera Node/UsersService.

PostgreSQL NO genera el UUID mediante DEFAULT.

Se decidió que email debe ser UNIQUE desde el principio porque representa una invariante de persistencia razonable.

Todavía NO se ha decidido ningún tratamiento especial para mayúsculas/minúsculas de email. Por ahora se utiliza el comportamiento normal de PostgreSQL.

No se han añadido:

* created_at
* updated_at
* deleted_at
* version
* índices adicionales
* relaciones
* migraciones
* ORM

No introducir estas cosas hasta que exista una necesidad real.

POSTGRES USER REPOSITORY

Ya existe:

src/repositories/PostgresUserRepository.ts

Implementa:

UserRepository

Recibe un Pool mediante constructor.

La dependencia se inyecta así:

constructor(private pool: Pool) {}

No importa directamente el pool desde postgres.ts.

Esto se decidió porque app.ts es el Composition Root y estamos haciendo Dependency Injection manual.

No se utiliza contenedor DI.

Implementación conceptual actual:

import { Pool } from "pg";
import { User } from "../types/User.js";
import { UserRepository } from "./UserRepository.js";

export class PostgresUserRepository implements UserRepository {
constructor(private pool: Pool) {}

async save(user: User): Promise<User> {
const result = await this.pool.query<User>(
`INSERT INTO users (id, name, email)
VALUES ($1, $2, $3)
RETURNING id, name, email`,
[user.id, user.name, user.email]
);

const savedUser = result.rows[0];

if (!savedUser) {
throw new Error("User was inserted but could not be retrieved");
}

return savedUser;
}

async findAll(): Promise<User[]> {
const result = await this.pool.query<User>(
`SELECT id, name, email
FROM users`
);

return result.rows;
}

async findById(id: string): Promise<User | undefined> {
const result = await this.pool.query<User>(
`SELECT id, name, email
FROM users
WHERE id = $1`,
[id]
);

return result.rows[0];
}
}

IMPORTANTE SOBRE LOS ERRORES DEL REPOSITORY

PostgresUserRepository NO conoce AppError.

Si PostgreSQL lanza un error de persistencia:

save()
↓
PostgreSQL error
↓
throw

El repository deja propagarse el error.

Si un INSERT correcto no devuelve ninguna fila mediante RETURNING, el repository lanza un Error genérico:

throw new Error("User was inserted but could not be retrieved");

Motivo:

* es una inconsistencia inesperada de infraestructura;
* AppError contiene conceptos de aplicación/HTTP;
* la capa de persistencia no debe conocer HTTP ni statusCode.

Todavía NO hemos decidido cómo traducir los errores específicos de PostgreSQL, como una violación de UNIQUE, a errores de aplicación.

Esto es precisamente el siguiente problema que debemos estudiar.
